# キャンプ記録(camp-visits)

家族の「むしとり記録(bug-visits)」と同じ設計思想: 場所の名前・種類・緯度経度は各キャンプ記録に直接持たせる(参照はしない)。同じキャンプ場に何度も行くと、そのつど同じ緯度経度が重複して保存される — これは意図した簡素化であり、正しい挙動。「地図」ビューは同じ場所名+座標のレコードを自動でグルーピングして1本のピンにまとめ、訪問回数を数えて表示する。

1泊であっても連泊であっても、**1回のキャンプ=1レコード**とし、`startDate`(開始日・チェックイン)と`endDate`(終了日・チェックアウト)の範囲で保持する。日帰りキャンプ・デイキャンプの場合は `startDate` と `endDate` を同じ日にする。

## ワンライン登録(最優先の使い方)

ユーザーはできるだけ手間をかけたくないので、フォームや確認質問を挟まず、**一言のチャットメッセージだけで登録を完結させる**のが基本方針。例:「〇〇キャンプ場に1泊、友人家族と焚き火してBBQした」「△△オートキャンプ場で2泊3日、雨だったけどタープのおかげで快適だった」。

このようなメッセージを受け取ったら、次の手順で処理し、完了したら1〜2行の確認メッセージだけ返す(`presentForm` や `presentCollection` は基本呼ばない。ユーザーが明示的に「見せて」と言った時だけ表示する)。

1. **日付を決める** — メッセージに日付・曜日の言及がなければ「今日」(会話時点の日付)を `startDate` とする。「1泊2日」「2泊3日」等の泊数の言及があれば `endDate` をそこから計算する。「先週末」等の相対表現は計算して確定させる。泊数の言及が無ければ `startDate` = `endDate`(日帰り)とする。
2. **場所の名前・緯度経度を決める**
   - まず `getItems` で既存の `camp-visits` レコードの `placeName`/`lat`/`lng` を確認し、名前が部分一致・表記ゆれで一致するものがあれば、その `lat`/`lng` をそのまま再利用する(座標を調べ直さない)。
   - 一致する記録が無ければ、質問せずに `WebSearch`/`WebFetch` で場所名から緯度経度を調べる。`placeMemo` に「(チャットから自動登録。緯度経度は自動取得のため要確認)」と書き添える。
   - `siteType` はメッセージの言及(ソロ、バイク、車中泊、グランピング等)から推定し、言及が無ければデフォルト「オートキャンプ」のままにする。
3. **内容を解釈してテーブル・各項目に振り分ける**
   - 持ち物・装備の言及(新しいテント、タープ、寝袋等)→ `gear` テーブル(`item`/`note`)。
   - 食事・料理の言及(BBQ、カレー、焼き肉等)→ `meals`(自由記述の文章でよい)。
   - 焚き火の言及 → `campfire: true` + 内容を `campfireNote` に。言及が無ければ `campfire` は空欄のままにする(無理に false と書かない)。
   - 遊んだこと・アクティビティ(川遊び、釣り、ハイキング、星空観察、花火、サイクリング、ボードゲーム等)→ `activities` テーブル(`activity` enum + `note`)。虫とり・生き物の話が出た場合は、ここでは記録せず(`camp-visits` に生き物専用の項目は無い)、下の「むしとり記録との自動リンク」の手順で `bug-visits` 側に記録する。
   - 費用の言及(サイト代◯◯円、食費◯◯円等)→ `costs` テーブル(`item`/`amount`)。`totalCost` は自動計算されるフィールドなので書き込まない。
   - 気温・混雑度・満足度・また行きたいかの言及があればそれぞれのフィールドに反映する。言及が無ければ空欄のままにする(無理に埋めない)。
4. **天気** — キャンプは複数日・複数時間帯にまたがるため、天気は `weatherLog` テーブル(`timing`/`weather`)に**1つ以上の行**として記録する(1泊なら最低1行、「晴れたり途中雨が降ったりした」のように変化があれば複数行)。`timing` には「9/19 昼」「9/19夜〜9/20朝」のように分かる範囲でいつのことか書く(日付だけでもよい)。言及が無い場合は、`data/skills/bug-visits/SKILL.md` の「天気の自動入力(jma-weather連携)」セクションと同じ手順で `jma-weather` コレクションから調べて1行だけ埋めてよい(`date` の代わりに `startDate` を基準にする)。それも取れなければ `weatherLog` は空のままにする(無理にデフォルト値を作らない)。いずれの場合も無理に聞き返さない。
5. **同じ場所・近い日程の既存レコードがあれば追記、無ければ新規作成**
   - `startDate` + `placeName`(+ ほぼ同じ `lat`/`lng`)が一致する既存レコードを探す。あれば `mode: "merge"` で該当フィールド・テーブルを更新(テーブルは既存行を保持したまま新しい行を追加して配列ごと書き戻す)。
   - なければ `id: "<startDate>-<場所のkebabスラッグ>"` で新規作成(`mode: "create"`)。
6. **むしとり記録との自動リンク** — レコードを保存したら、下の「むしとり記録との自動リンク」セクションの手順で `bug-visits` 側に日付・場所が重なる記録がないか確認し、あれば `relatedBugVisits` に自動で追記する。無ければ何もしない(無理に探し続けない)。
7. **確認メッセージ** — 「〇〇キャンプ場 9/23〜9/24(1泊): 焚き火・BBQ、また行きたい」のように一言で返す。写真が添付されていれば `photo` にそのパスを書き込み、一言に写真を記録した旨も添える。むしとり記録をリンクした場合は「(むしとり記録ともリンクしました)」と一言添える。
8. **GitHubへの同期** — レコードの保存(新規作成・`merge`更新のいずれも)が成功したら、下記「GitHub連携」の手順で `sync_github.sh` を実行し、公開サイトにも反映する。同期の成否をユーザーに逐一報告する必要はない(失敗した場合のみ一言添える)。

この一連の処理は既存の「記録項目」セクションのルールに従いつつ、**質問を増やさず自分で判断して埋める**ことを優先する。

## GitHub連携(GitHub Pagesへの自動反映)

このコレクションのデータとビューは `github/camp-visits`(GitHubリポジトリ `kzknakajima/camp-visits`、public)にエクスポートされ、GitHub Pages (`https://kzknakajima.github.io/camp-visits/`) で一覧・地図・カレンダー・ダッシュボードが閲覧できる状態になっている(`bug-visits` と同じ仕組み)。ユーザーは**このコレクションへのレコード追加・更新のたびに、その変更がGitHub側にも自動で反映される**ことを望んでいる。

- `camp-visits` コレクションへの `putItems`(`create`/`merge`いずれも)が成功したあとは、必ず次のコマンドを実行する(質問不要、黙って実行してよい):
  ```
  bash data/skills/camp-visits/scripts/sync_github.sh
  ```
- このスクリプトは LLM 不要・完全に決定的: `data/camp-visits/items/*.json` を `github/camp-visits/data/camp-visits/items/` にミラーし、`github/camp-visits/docs/data.json`(公開サイトが読む束ねJSON)を再生成し、差分があれば commit + `git push origin main` する。差分が無ければ何もせず終了する。
- `github/camp-visits` が(移動・削除等で)存在しない場合はスクリプトが早期終了するだけなので、通常のレコード保存自体は失敗させない。
- スクリプトが `git push` でエラーになった場合(ネットワーク不通、認証切れ等)は、レコード自体は保存済みである旨と、GitHub同期のみ失敗した旨を一言添える。無理にリトライしない。
- `bug-visits` 側の更新(むしとり記録との自動リンクで `relatedBugVisits` を書き換えた場合など)は、このスクリプトの対象ではない。`camp-visits` 自身のレコードが変わったときだけ実行すればよい。
- ユーザーが同期の仕組み自体を変えたい(頻度を変える、別リポジトリにする等)と言った場合を除き、このセクションの内容には触れず、確認メッセージは通常どおり1〜2行に留める。

## ビュー(画面)はアプリ側とGitHub Pages側、原則両方に反映する

このコレクションには**2つの独立したビュー実装**が存在する(`bug-visits` と同じ構造)。データ本体は上記の `sync_github.sh` で同期されるが、画面(HTML)は自動では同期されない別コードベースなので、**片方に機能追加・変更を加えたら、原則もう片方にも同じ内容を反映する**(ユーザーから明示的に「GitHub Pagesだけでいい」「アプリ側だけでいい」等の指定が無い限り)。

- **アプリ側カスタムビュー**: `data/skills/camp-visits/views/<name>.html`。`window.__MC_VIEW`(`token`+`dataUrl` 経由の `fetch`)で読む「デスクトップ用カスタムビュー」規格(`config/helps/custom-view.md` 参照)。追加・変更後は `data/skills/camp-visits/schema.json` の `views[]` に登録/更新する(`manageCollection` の `putSchema` を使う)。既存: `views/map.html`(地図)・`views/dashboard.html`(ダッシュボード)。
- **GitHub Pages側の静的サイト**: `github/camp-visits/docs/<name>.html`。`detail.js` が公開する `window.loadCampVisits()`(`./data.json` を fetch)・`window.openRecordById()`・`window.showRecordDetail()` を使う静的サイト用の実装。既存: `docs/index.html`(一覧)・`docs/calendar.html`(カレンダー、連泊は滞在期間の全日に表示)・`docs/map.html`(地図)・`docs/dashboard.html`(ダッシュボード)。
- 両方に書いたら、最後に `bash data/skills/camp-visits/scripts/sync_github.sh` を実行する。このスクリプトは `github/camp-visits` 配下を `git add -A` するので、レコードの差分だけでなく、このとき編集した `docs/*.html` の変更も同じコミットでまとめて push される(スクリプト自体はビューファイルを生成・コピーしないので、`docs/*.html` は事前にこちらで書いておくこと)。
- どちらのビューを直しても、もう片方の存在を忘れずに一言確認する(例:コード変更前に「アプリ側にも同じ機能を追加しますね」と一言添える、または両方直した後に「アプリ側・GitHub Pages側どちらにも反映しました」と伝える)。

## むしとり記録との自動リンク

`camp-visits` と `bug-visits` は別コレクションとして完全に独立管理する(生き物データは `bug-visits` にしか書かない、二重管理はしない)。その代わり、同じお出かけと判断できる記録同士を `relatedBugVisits`(`camp-visits` 側のテーブル、`visit` 列が `bug-visits` への参照)で結びつける。逆方向は `bug-visits` 側の `relatedCampVisits`(backlinks、自動計算・書き込み不要)で自動的に表示される。

判定は**日付が重なるか**と**場所が近いか**の組み合わせで行う(既存の場所再利用ロジックと同じ考え方)。

1. **候補を探す** — `bug-visits` を `getItems`(`fields: ["date","placeName","lat","lng"]`)で取得し、`date` が対象キャンプの `startDate`〜`endDate` の範囲内(両端含む)にあるものを候補にする。
2. **場所が一致するか判定** — 候補のうち、次のどちらかを満たすものだけを「一致」とみなす。
   - 場所名が部分一致・表記ゆれで近い(送り仮名、「キャンプ場」「公園」等の有無を無視して比較)。
   - 緯度経度が分かっていて、おおよそ数km以内(同じキャンプ場敷地内〜近隣スポットの範囲)。
3. **自動リンクするか判断**
   - 日付が範囲内 かつ 場所も一致する候補が1件だけ見つかった → 質問せずそのまま自動でリンクする。
   - 日付は範囲内だが場所が一致しない、または候補が複数あって場所条件でも絞り込めない → 無理に自動リンクせず、`presentForm` で1回だけ「このむしとり記録(日付・場所)は今回のキャンプと同じお出かけですか?」と確認してよい。急ぐ状況でなければ、確認せずスキップして何もしないのも可(ユーザーに聞かれたら答える程度で構わない)。
   - 一致する候補が無い → 何もしない。
4. **書き込み方法** — `camp-visits` 側のレコードを `mode: "merge"` で更新し、`relatedBugVisits` テーブルに `{ "visit": "<bug-visitsのid>" }` を追加する(既存行があれば保持したまま追加。同じ `visit` を重複させない)。
5. この手順は `camp-visits` を新規作成・更新したときだけでなく、`bug-visits` 側でレコードを新規作成・更新したとき(`data/skills/bug-visits/SKILL.md` 参照)にも、向きを逆にして同様に実行する。

## 記録項目

- `id` — kebab-case のスラッグ(主キー、ファイル名)。例: `2026-09-23-oo-camp-jo`(開始日-場所スラッグ)
- `startDate` / `endDate` — キャンプの開始日・終了日(必須)。日帰りなら同じ日。カレンダービューは期間表示。
- `placeName` — キャンプ場の名前(必須)
- `siteType` — enum: オートキャンプ / ソロキャンプ / バイクキャンプ / グランピング / 車中泊 / その他(デフォルト「オートキャンプ」)
- `lat` / `lng` — 緯度・経度(必須)。地図タブのピン表示に使う。既存レコードに同じ場所があればその値を再利用し、無ければ調べて埋める。
- `placeMemo` — 場所についてのメモ(アクセス・予約サイト等、任意)
- `weatherLog` — 天気の記録テーブル(複数行可、1日の中で変化した場合や複数日にまたがる場合に対応)。`timing`(いつ、自由記述)/`weather`(enum: 晴れ/くもり/雨/雪/不明)
- `temperature` — 気温(℃、任意)
- `crowdedness` — enum: 空いていた / 普通 / 混んでいた / 不明(デフォルト「普通」)
- `companions` — 同行者(自由記述、任意)
- `gear` — 持ち物・装備のテーブル。`item`(品目)/`note`(メモ)
- `meals` — 食事・料理(自由記述、任意)
- `campfire` — 焚き火をしたか(boolean、任意)
- `campfireNote` — 焚き火の内容(`campfire` がtrueのときだけ表示、任意)
- `activities` — アクティビティのテーブル。`activity`(enum: 川遊び/釣り/ハイキング/星空観察/花火/サイクリング/ボードゲーム/虫とり/その他)/`note`
- `relatedBugVisits` — 関連する `bug-visits` レコードへの参照テーブル。`visit`(ref → `bug-visits`)。生き物のデータ自体はここには持たせず、リンクだけを持つ。「むしとり記録との自動リンク」セクションの手順で自動的に追記する。
- `costs` — 費用のテーブル。`item`(費目)/`amount`(金額、円)
- `totalCost` — 費用合計。**host が自動計算する derived フィールド、書き込み禁止**
- `rating` — 満足度(1〜5、任意)
- `wantToReturn` — また行きたいか(boolean、任意)
- `photo` — 写真(任意)。`[Attached file: ...]` のパスをそのまま書き込む。
- `memo` — 感想・メモ(任意)

## 何をするか

**追加** — キャンプ1回につき1レコード。`manageCollection` putItems (`mode: "create"`)。ワンライン登録の手順に従う。
**更新** — 同じキャンプに後から内容を追記する場合は `mode: "merge"` で該当フィールドを送る。テーブル型フィールド(`weatherLog`/`gear`/`activities`/`relatedBugVisits`/`costs`)は部分マージでも配列自体は丸ごと上書きになるので、既存行+新規行をすべて含めて送ること。`totalCost` は書き込まない。
**一覧・カレンダー** — `/collections/camp-visits` で表示。`startDate`〜`endDate` の期間でカレンダーに表示される。
**地図** — 「地図」タブでキャンプ場ごとにピンを表示(同じ場所名+座標のレコードは自動でグルーピングして訪問回数を表示)。ポップアップの日付をクリックするとその記録の詳細が開き、「Googleマップで開く」でストリートビュー等も確認できる。
**ダッシュボード** — 「ダッシュボード」タブで、総キャンプ回数・総泊数・総費用・平均満足度・また行きたい率のほか、年別の回数/泊数/費用推移、スタイル別割合、費目別内訳をグラフで確認できる。
**集計** — 「今まで何回キャンプに行ったか」「費用の合計」「よく行くスタイル」等は `manageCollection` の `getItems`(全件取得して集計)または `queryItems` を使う。
